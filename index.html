▸展开：架构 · 负责的四块 · 三次线上问题
负责的四块
  • RAG 检索链路：以字段元数据、Few-shot 用例、指标别名三类向量集合（67 / 104 / 74 条）为检索源，最小检索单元是「一个字段 / 一条用例 / 一个别名」；用 Join 图 BFS 最小边集补全多表拓扑，用粒度对齐防止一对多 JOIN 把金额放大；以 score_threshold + payload 过滤 + 业务优先级剪枝替代两阶段 rerank，省掉一次模型调用。
  • 指标语义层：12 个核心指标的口径（公式 / 过滤条件 / 时间归属 / 可用维度 / 权限标签）配置化落库，由统一取数规划器翻译成只读 SQL——口径变更不发版，代码侧零硬编码公式。
  • 缓存与并发：缓存键强制包含权限范围哈希（否则 A 用户的结果会被 B 用户命中，这是最典型的数据泄露路径）；single-flight 请求合并削峰；分布式锁 SET NX PX 原子获取 + Lua 校验持有者删除 + 长任务按锁时长 1/3 续期；「锁 + 幂等表」双层保证日报推送幂等。
  • 多智能体编排：LangGraph StateGraph 把 15 节点主链路固化为代码控制流（仅 5 处条件边），取代自由 Agent 循环；会话状态经 Checkpointer 持久化。
三次线上问题的定位与修复
一对多 JOIN 让归因结论被挤出 Top3

一次异动归因，系统把主因算到了品类上，与业务判断对不上。根因：品类维度 JOIN 明细表后仍沿用订单级金额求和，一个订单含多商品时金额被重复累加——数字量级「看起来像那么回事」、不报错，只有排名异常才暴露。改为明细金额聚合，并用造数保证「明细金额之和 == 订单实付金额」，整月差值 0。

权限校验 30 项全绿，而条件注入完全没生效

根因是校验脚本自己拼了一遍权限条件再比数字——测试复述了设计意图，没有断言执行路径。重写为 28 个越权用例直接检查权限改写函数的产出，第一次运行就抓出 4 个缺陷，最终 100% 拦截。

并发压测成功率 0%：async def 里跑同步 I/O

声明为 async 的函数内部执行同步阻塞调用，事件循环被拖死——「看起来并发的代码」实际完全不并发。重建并发链路后 P95 从 26.6 s 降到 4.18 s，压测另外抓出 3 个并发缺陷。

技术选型
为什么不用自由 Agent
业务链路固定，自由循环换来的是不可复现的失败；固化成状态机后每一次失败都能重放到具体节点。
为什么不让模型写 SQL
模型负责「理解问题 + 拼装结构」，SQL 由语义层编译；模型输出永远不直接进执行路径。
为什么不做 rerank
结构化检索的候选集很小且带业务标签，阈值 + payload 过滤已足够，省一次模型调用的延迟与成本。

任务规划与三道校验

Agent 安全靶场：提示注入红队与防御评测

解决什么问题

Agent 一旦带上工具（读文件 / 查库 / 发消息 / 发请求），一段藏在文档里的提示注入就能把数据带出去。这类风险需要一套可量化、可对比的评测口径。

为什么做这个

带工具的 Agent 一旦被提示注入命中，风险发生在工具调用上：模型能拒绝直接的恶意指令，却可能照着文档里的伪造指令去读文件、查库或请求外部地址。这个项目把这件事变成可测量的数字：不可信输入不进执行路径——在 SQL 上是 AST 白名单与权限下推，在 Agent 上是工具白名单与轨迹断言。

评测方法
  • 命中判定：断言工具调用序列——是否调用了越权工具、参数是否含敏感路径、外发请求是否携带密钥；以工具执行成功作为攻破判据，被拦截的调用不计入。
  • 误杀对照：每个配置同时跑一组不含攻击的正常任务，防御导致正常任务失败会计入误杀率。
实测结果
  • 效果：24 条自适应攻击各跑 2 轮，防御全关被攻破 28.3%，防御全开 0 漏；换一家厂商的模型重跑同一套用例，基线升到 52.2%，全开仍是 0。
  • 逐层消融：五层防御逐一关掉后复测，只有工具白名单这一层会重新出现攻破，说明它是这组攻击面的关键防线；其余四层在这批用例上没有额外贡献。
  • 对照测试：把伪造指令做成图片送进多模态模型，以及 base64、全角同形字、HTML 注释、CSV 公式等编码混淆载荷，均未出现绕过。
  • 工程质量：38 条单元测试与端到端回归全绿，GitHub Actions 在 Python 3.11 / 3.12 上自动跑。

▸展开：五个设计决策
五个设计决策
  • 协议驱动渲染：每类物料声明 props_schema（属性结构 / 数据契约 / 默认值），属性面板自动生成——新增组件只注册物料、不改编辑器，把开闭原则落到代码结构上（8 类物料）。
  • 表达式不开放 eval：表达式来自业务配置，等于把执行权交给配置人员。自研递归下降解析器把它变成自己的 AST，语法里根本没有属性访问、下标、import，所以 __import__('os').system(...) 连解析都过不去。
  • 权限下推到最内层 WHERE：不做「查完再过滤」——那样可以用「总数 − 可见明细」反推隐藏数据。条件注入到每个直接读取目标表的 SELECT，并用该层别名限定列名，避免 JOIN 歧义列报错。
  • 粒度对齐：orders ↔ refunds 是 1:N 且非粒度对齐，直接 JOIN 会让 SUM(pay_amount) 按退款条数翻倍；编译器先把退款按 order_id 预聚合到订单粒度，再 LEFT JOIN。
  • 发布快照 + 缓存键含权限指纹：草稿 / 发布双态、发布生成快照可回滚；缓存键强制包含权限范围指纹，避免跨权限命中。
模型在这里的位置

自然语言 → 页面 DSL 只产出候选，不做任何直接执行；候选经 AST 白名单校验 + 试渲染双重把关，校验失败把错误信息回灌重新生成。模型能力与确定性边界各自负责一段，出问题能定位到是哪一段。

受限用户只能看到其权限范围内的部分数据，且无法用「总数 − 可见明细」反推隐藏部分。

五条工程信条

从项目里沉淀下来的五条做法。

01
模型只做理解与拼装，规则必须落在确定性代码里

口径、权限、SQL 结构由语义层与 AST 校验承担，模型输出永远不直接进执行路径。这样出错时能定位到「是理解错了，还是规则没覆盖」。

落地：指标语义层（12 指标）、sqlglot 七类校验、权限下推最内层 WHERE。

02
测试要断言执行路径，不照设计复述

权限校验 30 项全绿，而权限条件注入完全没生效——因为脚本自己拼了一遍条件再比数字。测试如果照着设计写，就只是在验证「我以为」。重写后 28 个越权用例第一次运行就抓出 4 个缺陷。

03
粒度不对齐比语法错误危险得多

JOIN 放大不报错、量级看着合理，只让排名悄悄错掉。修法是造数断言「明细之和 == 订单实付」；低代码平台里同样先用预聚合对齐粒度再 LEFT JOIN。

04
并发能力靠压测检验

async def 里跑同步 I/O，压测成功率 0%、P95 26.6 s——「看起来并发」和「实际并发」之间没有中间地带。重建链路后 P95 4.18 s，压测还顺手抓出 3 个并发缺陷。

05
降级优先于失败

除配置与元数据库外，任何依赖不可用都不阻止启动：Redis 挂了退本地、Qdrant 不可用退全表元数据、ES 不可用只写库。可用性先于完整性。
